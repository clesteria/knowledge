#[[nim]] #[[FromGeneratedAI]]

## スタイル

- 公式スタイルガイドにより、変数名とプロシージャ名はキャメルケース、型(type)名はパスカルケースで書くことが推奨されている。
- nim は識別子の先頭の文字以外は大文字小文字を区別しない仕様がある。

## スコープ

- シンボルのアスタリスク `*`: 型や手続き名の後ろに付く `*` は、そのシンボルがモジュール外部に公開、エクスポートされていることを示す。
  - `*` を付けないシンボルは、そのモジュール内でのみ有効な「プライベート」な存在となり、外部からアクセスすることはできない。これは**カプセル化**に寄与する。
  - フィールドのエクスポート: `object` のフィールドに `*` を付けると、そのフィールドも外部モジュールからアクセス可能になる。
- ディレクトリ構造のような「親子関係」は、Nim のモジュールの可視性に一切影響しない。
  - 他のモジュールからアクセスできるかどうかは、エクスポートされているかどうかのみで決まる。
  - エクスポートされたプロシージャやフィールドは、他のモジュールから `import` することで利用できる。

#### シングルトン

- プログラム全体でインスタンスが一つしか存在しないことを保証するパターン。
- Nim では、モジュールの性質を利用して簡単に実現できる。
  - モジュールのトップレベルにプライベートな変数としてインスタンスを置き、それを返す公開プロシージャを用意する。
- グローバルな状態を生み出し、テストを困難にし、依存関係を隠蔽するという欠点があるため、扱いには注意が必要となる。

#### 他言語とのモジュール/可視性の比較

| 言語           | 公開（エクスポート）方法                    | 特徴                                                                |
| :------------- | :------------------------------------------ | :------------------------------------------------------------------ |
| **Nim**        | シンボル名の末尾にアスタリスク `*` を付ける | 明示的。付けなければモジュールプライベート。                        |
| **JavaScript** | `export` キーワードを付ける                 | Nim と非常に似た思想。明示的。                                      |
| **Python**     | デフォルトで全て公開                        | アンダースコア `_` で始まる名前は非公開、という慣習。強制力はない。 |
| **Go**         | シンボル名の最初の文字を**大文字**にする    | シンプルで強力なルール。コンパイラが強制する。                      |
| **Java**       | `public` などのアクセス修飾子を使う         | クラスベースの厳密なアクセス制御。                                  |

### 変数

- モジュールのトップレベルで宣言された変数は、そのモジュール内でのグローバル変数（または`const`の場合は定数）となる。
- `var`
  - 再代入可能な**可変**変数。
  - 値は**実行時**に決定される。
- `let`
  - 再代入不可能な**不変**変数。
  - 値は**実行時**に決定される。
  - 関数内で引数によって値が決まるが、その後の処理で変更されないような場合に使うと、コードの意図が明確になり安全性が高まる。
- `const`
  - **不変**の定数。
    - プログラム全体を通して不変。
  - 値は**コンパイル時**に決定される必要がある。

### enum

- `type Name = enum foo, bar` で Name 型の enum を定義する。
- _$演算子(dollar operator)_ により、 _文字列化プロシージャ_ を定義できる。
  - _文字列化プロシージャ_ は指定した型の値を文字列に変換する対応を定義するために使う。
  - 名前の通り、文字列化のみに使うため、型の値を文字列以外の型の値に変換する場合、そのためのプロシージャ(例えば toInt プロシージャ)を自分で実装する必要がある。
  - _文字列化プロシージャ_ を作成済みの enum に対して、int へキャストすることで内部の数値を扱うことができる。
- ただ各列挙子に対して文字列を定義したいのであれば、型の定義時に、`type Name = enum foo = "ほげ", bar = "ふげ"`のように _文字列マッピング_ を書くことで、 _文字列化プロシージャ_ は不要。

### case

- **`case` にタプルは使えない！**
- `Error: selector must be of an ordinal type, float or string` というエラーが出る。

### 参照

- `ref object`と宣言したオブジェクトは参照型となり、モジュール間でやりとりする際に参照するアドレスが渡される。
  - 参照を通じたデータの変更は、大元のデータの変更となる。
  - 他の言語では _参照渡し_ と言われる仕組みだが、 nim は仕様として参照渡しという概念を持たない。
- 参照型のオブジェクトはヒープ領域に格納される。

#### 参照型の挙動

をプロシージャの引数で渡した場合、渡されるのはオブジェクトの「住所」である。そのため、プロシージャ内でその参照を通じてオブジェクトの中身を変更すれば、大元のオブジェクトが直接変更される。

したがって、**プロシージャの最後に`return`でそのオブジェクトを返さなくても、加えられた変更は呼び出し元に反映される。**

#### 値型 (`object`) vs. 参照型 (`ref object`)

| 項目             | `object` (値型)            | `ref object` (参照型)                              |
| :--------------- | :------------------------- | :------------------------------------------------- |
| **実体**         | データそのもの             | データへの**参照（ポインタ）**                     |
| **メモリ領域**   | スタック                   | ヒープ                                             |
| **代入時の挙動** | 全データが**コピー**される | 参照（アドレス）が**コピー**される（データは共有） |
| **引数渡し**     | コピーが渡される           | 参照が渡される（効率的）                           |

コンテキストオブジェクトや、ゲームの`Player`のように「状態を共有・変更」する必要があるデータは、`ref object`で定義するのが極めて効果的である。

### 標準ライブラリ

#### json

- JSON データのパース（解析）と生成のためのプロシージャを提供する。
- JsonNode 型を使って JSON 構造を表現する。

#### tables

- キーと値のペアを格納するハッシュテーブル（辞書、マップ）を提供する。
- Nim では Table 型として利用できる。
- 実用例
  - enum に対する添え字に影響しない値を定義するための Table 型を用意
  - JsonNote 型 を Table 型に変換して扱いやすくする

##### strutils

- 文字列操作のためのユーティリティプロシージャを提供する。
- 文字列の変換、分割、結合、検索などができる。
- 実用例
  - parseInt プロシージャは、受け取った文字列を整数に変換して返す
  - toLower プロシージャは、受け取った文字列のアルファベットを小文字に変換して返す
  - stdin.readLine プロシージャは、標準入力から読み込んだ入力文字列を返す

##### sequtils

- シーケンス（動的配列）操作のためのユーティリティプロシージャを提供する。
- シーケンスのフィルタリング、マッピング、結合などができる。
- 実用例
  - map プロシージャは、シーケンスを受け取り、無名関数による結果を新しいシーケンスとして返す。
  - zip プロシージャは、2 つのシーケンスの要素をペアにしてタプルとして返す。

##### options

- 値が存在しない可能性を安全に扱うための Option 型を提供する。
  - NullPointerException のような問題を避けるのに役立つ。
- some で値があることを示し、none で値がないことを示す。
- isNone や get などのプロシージャで値を安全に操作できる。

##### random

- 乱数生成のためのプロシージャを提供する。
- `randomize()` でシードの初期化を行う。
  - シード値の固定を行う場合、`setRandSeed([int])`を代わりに使用する。
- `randomize()` や `setRandSeed()` はグローバルな乱数生成期の状態を初期化する。プログラム実行時の一番最初に一度だけ実行させるもの。

##### staticio

- コンパイル時にファイルを読み込み、実行可能ファイルに埋め込むためのプロシージャを提供する。
  - これにより、実行時に外部ファイルに依存することなくデータを扱えるようになる。
- 各種値の定義を JSON ファイルとして用意している環境下で、リリースビルド時のみ staticio モジュールによりバイナリに埋め込む、と言った際に使用する。
  - リリースビルドでは JSON ファイルが配布パッケージに不要となり、データの改竄を難しくする。

### コンパイラ

#### オプション

- `-d:danger`: 配列の境界チェックや`nil`チェックといった、実行時の安全チェックをすべて無効にする。これによりプログラムは高速に動作するが、バグがあった場合に即クラッシュする危険なコードになる。パフォーマンスを最優先するリリースビルドなどで使用される。
- `--gc:orc`: ガベージコレクション（GC）の方式として、リアルタイム GC である`orc`を指定する。`orc`は、従来の GC のようにプログラムの実行を長時間停止させることがほとんどないため、ゲームや GUI アプリなど応答性が重要なアプリケーションに適している。最近の Nim ではデフォルトの GC となっている。

#### GC を使わない開発 (`--gc:none`)

- **概要**: コンパイル時に `--gc:none` を指定すると、GC 機能が完全に無効化される。これにより、`new` や、`string`, `seq` といったヒープメモリを内部で利用する標準型がそのままでは使えなくなる。
- **メモリ管理**: プログラマは `system` モジュールの `alloc` や `dealloc` を使い、C 言語のように手動でメモリを確保・解放する全責任を負う。
- **利点**: メモリ管理を完全に制御でき、GC によるパフォーマンスへの影響がゼロになる。
- **欠点**: 開発が非常に複雑になり、メモリリークやダングリングポインタといったバグを生み出しやすい。
- **用途**: OS カーネル、組み込みシステム、超低レイテンシが要求される金融システムなど、ごく一部の特殊な分野に限られる。通常のアプリケーション開発で選択することはまずない。

#### スタック中心のプログラミング

- **概要**: そもそも GC が問題になるヒープメモリの使用を避け、可能な限りスタックメモリ上で処理を完結させるプログラミングスタイル。
- **方法**:
  - `ref object` や `ptr object` の代わりに、値型である `object` を積極的に利用する。
  - プロシージャのローカル変数として宣言された値型オブジェクトはスタックに確保され、プロシージャを抜ける際に自動的に解放されるため、GC は関与しない。
- **利点**: 非常に高速で、メモリ管理についてプログラマが意識する必要がほとんどない。
- **欠点**: プロシージャのスコープを超えて存続するような、複雑なデータ構造や長寿命のデータを扱うのが難しい。
- **用途**: 小規模な処理や、特定のアルゴリズムの実装など、データの寿命が明確な場合に有効。

### プロシージャとマクロ

- **違い**: プロシージャは**実行時**に**値**を操作するが、マクロは**コンパイル時**に**コードそのもの (AST)** を操作する。

|                | プロシージャ                             | マクロ                                                                   |
| -------------- | ---------------------------------------- | ------------------------------------------------------------------------ |
| タイミング     | 実行時に呼び出される。                   | コンパイル時に展開され、コードに変換される。                             |
| 引数           | 評価済みの「値」を受け取る。             | 「コードの断片」を受け取る。                                             |
| 役割           | マクロに適してない処理のすべて。         | コードを生成・変換する。DSL の構築や、ログ出力等定型コードの削減に使う。 |
| コンパイル時間 | 短い                                     | 長い                                                                     |
| パフォーマンス | 実行時に呼び出しのオーバーヘッドがある。 | 実行時の呼び出しコストがなくなるため、実行速度は向上することが多い。     |
